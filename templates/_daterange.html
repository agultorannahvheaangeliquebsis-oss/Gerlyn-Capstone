/ like the topbar avatar menu, so it needs no JavaScript: the disclosure behaviour, keyboard handling and screen-reader semantics all come from the element. It therefore still works on a page whose JS failed to load. Presets are submit buttons in one GET form rather than links — only the clicked button contributes its `range` value, so presets and the custom Apply share a single mechanism, and the whole form serialises in one place. Context expected: active_range the preset actually applied, from range_from_request range_start/end resolved dates, used to seed the custom inputs daterange_carry list of (name, value) pairs for the page's OTHER filters, so choosing a range never silently drops the branch or search the user already set daterange_hide_all True hides the "All time" chip on surfaces that cannot render an unbounded range (the Dashboard buckets per day and needs a previous window of equal length). The server enforces this too — see range_from_request(allow_all=) — so hiding the chip is presentation, not the guard. NOTE: like the avatar menu, this does not close on outside-click without JS. That matches the existing component rather than introducing a new behaviour. {% endcomment %}
