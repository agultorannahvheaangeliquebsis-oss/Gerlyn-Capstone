on billing_detail and hidden by CSS until static/js/order-status-confirm.js opens it — so `reason` is an ordinary control of that form, exactly like partials/_order_status_confirm.html's pattern for order-status transitions. Not that same partial reused with a synthetic context: its summary is order-status-shaped (a from/to status pill transition), which doesn't fit a payment rejection, so this is a small billing-specific sibling instead. Usage: {% include "partials/_billing_reject_confirm.html" with record=record %} Everything here is display only: billing_confirm re-validates the reason, the transition and the maker/checker rule server-side. The hidden status input is what the dialog's own Reject button posts: a form submits only its submitter's name/value, and that button (unlike the trigger that opened the dialog) has none, so without it the request would arrive with no status and be refused as "Invalid payment status." {% endcomment %}
