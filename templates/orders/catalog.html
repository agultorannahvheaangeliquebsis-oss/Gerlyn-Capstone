{% comment %} Filter rail. The reference stacks Category, Brand and Price range here. Only the first survives as-is: Product has no brand/manufacturer column, so a Brand facet would be a list of headings with nothing behind them, and a min/max peso box only hides rows. Branch takes that space instead, because it is the filter with real consequences in this store — stock and the cart are per-branch, so choosing one changes what is actually buyable. It is a session choice rather than a query parameter (customer_views.set_branch / .clear_branch), which is why those entries are plain links while the categories carry ?category=. {% endcomment %}

Filters

{% comment %} One GET form for both blocks, with real inputs — the rail used to be two lists of links dressed as filters. Categories are CHECKBOXES because "Rice and Canned goods" is a reasonable thing to ask for, and the view reads them with getlist(). Branches are checkboxes too, but they mean something slightly different, and orders.customer_views.product_catalog documents the rule: ticking several BROWSES several branches, while the cart still needs exactly one. Tick a single branch and it becomes the branch you are shopping at; tick several and the storefront falls back to the same state as having chosen none, where the cards ask you to pick one before ordering. Ticking a box updates the grid immediately (catalog-live.js) — there is no Apply button, because there is nothing left for one to do. Clear stays a real link so the rail still works with JavaScript off; catalog-live.js intercepts its click when it's running, resetting the boxes themselves (not just the grid) before the same live fetch. No-JS fallback: with no submit button, an unticked box only takes effect once something else in this form submits (typing then pressing Enter has no field to press it in here, so in practice that means Clear, or a category/branch link elsewhere on the storefront). That trade is deliberate — the entire point of removing Apply is that nobody running JS should need a button at all. {% endcomment %}

Branch {% comment %} No "All branches" row: with checkboxes, all branches IS none ticked, and a box that unticks the others is a radio wearing a square. The empty hidden value is what makes unticking everything work. An unchecked checkbox submits nothing at all, so with no hidden field a shopper who cleared every branch would send no `branch` key — which the view reads as "no branch filter in this request, leave the session alone" and their last branch would stick. This guarantees the key is always present; the view drops it for not being a digit. {% endcomment %}
