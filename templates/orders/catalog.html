{% comment %} One GET form for both blocks, with real inputs — the rail used to be two lists of links dressed as filters. Categories are CHECKBOXES because "Rice and Canned goods" is a reasonable thing to ask for, and the view reads them with getlist(). Branches are checkboxes on the same footing: ticking any combination just filters the grid to what those branches stock. It does not touch the shopping branch or the cart — see the rule in orders.customer_views.product_catalog. The cards' own Add-to-cart / "Choose a branch" state still keys off the session's shopping branch, not off what is ticked here. Ticking a box updates the grid immediately (catalog-live.js) — there is no Apply button, because there is nothing left for one to do. Clear stays a real link so the rail still works with JavaScript off; catalog-live.js intercepts its click when it's running, resetting the boxes themselves (not just the grid) before the same live fetch. No-JS fallback: with no submit button, an unticked box only takes effect once something else in this form submits (typing then pressing Enter has no field to press it in here, so in practice that means Clear, or a category/branch link elsewhere on the storefront). That trade is deliberate — the entire point of removing Apply is that nobody running JS should need a button at all. {% endcomment %}

Branch {% comment %} No "All branches" row: with checkboxes, all branches IS none ticked, and a box that unticks the others is a radio wearing a square. The empty hidden value is what makes unticking everything work. An unchecked checkbox submits nothing at all, so with no hidden field a shopper who cleared every branch would send no `branch` key — which the view reads as "no branch filter in this request" and falls back to showing their session branch's stock, so their last branch would stick. This guarantees the key is always present (an explicit, possibly empty, branch filter); the view drops it for not being a digit. {% endcomment %}
