# GerlynPLUS date-field policy inventory

All user-entered calendar dates use the application's configured local day.
Future-action validation is based on `timezone.localdate()`, never the UTC
date and never the browser clock.

## Future-action dates

| Domain field / input | Meaning | Validation paths |
|---|---|---|
| `Procurement.proposed_delivery_date` | Delivery date offered or counter-offered during buyer/supplier negotiation | Both negotiation views call the shared validator, all proposal inputs publish `min=<local today>`, and final supplier confirmation revalidates before activating the agreed terms. |
| `Procurement.delivery_date` | Agreed expected delivery date, including manual rescheduling and API overrides | DRF `expectedDelivery`/`deliveryDate`, the rescheduling service, and the agreed-terms service boundary require today or later whenever a new commitment is written. Applicable HTML inputs publish `min=<local today>`. |

There are currently no separate scheduled-date or offer-date fields in the
schema. If one is introduced, it belongs in this table and must use
`core.date_validation.validate_today_or_future` at every input and mutation
boundary.

## Historical, factual, and reporting dates

These dates intentionally support past values and must not receive the
future-action validator.

| Domain field / input | Why past dates are valid |
|---|---|
| `Procurement.order_date` | Historical date on which the PO was raised; imports and corrections can predate entry. |
| `Procurement.actual_receipt_date`, `DeliveryReceipt.receipt_date`, and DRF `actualReceiptDate` | Actual receipt history may be entered retrospectively and is separate from the expected delivery commitment. |
| `StaffProfile.date_hired` | Employment history. |
| `StockTransfer.transfer_date` | Transaction/effective date of a withdrawal or transfer. |
| `Batch.received_date`, `OpeningStockImportRow.received_date` | Actual stock receipt history. |
| `OpeningStockImport.as_of_date` | Effective date of an imported opening balance. |
| Inventory, warehouse, batch, and opening-stock `expiry_date` fields | A product/lot fact, not a scheduled action. Past dates are needed to represent and dispose of expired stock; opening-stock validation warns rather than falsifying history. |
| Report and list `date_from` / `date_to` filters | Historical query boundaries. Past values remain allowed; only malformed or inverted ranges are rejected. |
| `SalesTransaction.transaction_date`, `BillingRecord.date_recorded`, and other `created_at`, `updated_at`, confirmation, authorization, scan, read, void, deletion, and resolution timestamps | System/audit history, normally generated by the server. |
| Session/challenge `expires_at` | System-generated security lifetime, not a user-selectable scheduled business date. |

The current customer profile has no birth-date field. A future birth-date
field is historical and must continue to allow past dates.

## Shared rules

- `core.date_validation.validate_today_or_future` is the single future-date
  comparison and emits `Date must be today or later.`
- `core.date_validation.validate_date_range` and `parse_date_range` enforce
  valid ISO dates and `date_from <= date_to` while retaining historical dates.
- Browser `min` attributes are usability hints only. Server-rendered views,
  DRF serializers, and service mutation boundaries enforce the same policy.
- The HTML minimum is rendered from the server's local date, so it agrees
  with server validation around UTC/local midnight.
